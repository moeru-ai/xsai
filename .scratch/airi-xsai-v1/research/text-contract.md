# Text contract research

Source revisions:

- xsAI: `3cabb2b045481b95b7ccde9a09080f23e2eb4ff5` (`1.0.0-beta.3`)
- AIRI: `3b0672e3668bd1ade1210e579818f379e4f8a224` (`0.12.0`)

This note covers text, messages, tools, streaming, cancellation, history, and the Responses patch. A step is one model request. A turn is AIRI's full request and tool lifecycle.

## Facts

### xsAI beta.3

- The v1 API uses a model function and a shared options object. A `LanguageModel` is `(options) => Promisable<ReadableStream<TextEvent>>`. The options use `input`, `maxOutputTokens`, `providerOptions`, `signal`, `tools`, and `toolChoice` ([packages/text/src/types/language-model.ts:8-29](../../../packages/text/src/types/language-model.ts#L8-L29)). The three adapter functions return a `LanguageModel` ([packages/text-chat/src/index.ts:24-48](../../../packages/text-chat/src/index.ts#L24-L48), [packages/text-messages/src/index.ts:27-67](../../../packages/text-messages/src/index.ts#L27-L67), [packages/text-responses/src/index.ts:25-50](../../../packages/text-responses/src/index.ts#L25-L50)).
- The model function captures transport settings. `HttpOptions` contains `apiKey`, `baseURL`, `fetch`, `headers`, and `model` ([packages/shared/src/types/http-options.ts:1-8](../../../packages/shared/src/types/http-options.ts#L1-L8)). Per-request `providerOptions` can change wire fields, but they do not replace this captured transport object ([docs/text/adapters.md:51-90](../../../docs/text/adapters.md#L51-L90)).
- Messages are stateless. The caller sends the full list again and preserves the returned assistant message. A tool loop needs every step message and a user message with each step's tool results ([docs/text/messages.md:8-32](../../../docs/text/messages.md#L8-L32)). Assistant messages can carry `providerMetadata`; assistant provider parts carry opaque values. A provider part is message content, not a request scope ([packages/text/src/types/message.ts:4-11](../../../packages/text/src/types/message.ts#L4-L11), [packages/text/src/types/content.ts:29-45](../../../packages/text/src/types/content.ts#L29-L45)).
- v1 user input has text, image, file, and tool-result Parts. A file has only `data: string | URL`. There is no audio Part, filename field, or provider file ID ([packages/text/src/types/content.ts:3-27](../../../packages/text/src/types/content.ts#L3-L27), [packages/text/src/types/message.ts:38-43](../../../packages/text/src/types/message.ts#L38-L43)). A tool result can contain only text and image Parts ([packages/text/src/types/content.ts:66-73](../../../packages/text/src/types/content.ts#L66-L73)).
- The adapters already have different media limits. Chat requires a base64 data URL for a file and rejects image tool results ([packages/text-chat/src/utils/normalize-input.ts:23-55](../../../packages/text-chat/src/utils/normalize-input.ts#L23-L55)). Responses accepts a data or HTTP URL for a file and maps provider Parts back into assistant input. It replays a provider Part only when its `source` matches the current Responses endpoint ([packages/text-responses/src/utils/normalize-input.ts:47-60](../../../packages/text-responses/src/utils/normalize-input.ts#L47-L60), `:111-161`).
- The v1 tool shape is `{ name, description?, inputSchema, outputSchema?, execute? }`. The execute context has only `signal` ([packages/text/src/tool.ts:8-31](../../../packages/text/src/tool.ts#L8-L31)). The loop validates input, runs calls in parallel, turns missing tools and thrown errors into `isError` tool results, and sends error results instead of running an incomplete length-limited call ([packages/text/src/utils/execute-tools.ts:45-109](../../../packages/text/src/utils/execute-tools.ts#L45-L109), [docs/text/tools.md:37-49](../../../docs/text/tools.md#L37-L49)).
- `prepareStep` runs before every model request. It can return a new `model` and any `LanguageModelOptions` except `signal` ([packages/text/src/types/prepare-step.ts:7-17](../../../packages/text/src/types/prepare-step.ts#L7-L17)). This supports a model swap, but it does not mutate the model function's captured `baseURL`, credentials, headers, or fetch function.
- `step.end` is one request terminal event. It has `completed`, `incomplete`, `cancelled`, or `failed` status. The event builder emits one terminal event and rejects a truncated stream ([packages/text/src/types/text-event.ts:37-63](../../../packages/text/src/types/text-event.ts#L37-L63), [packages/text/src/utils/event-builder.ts:232-295](../../../packages/text/src/utils/event-builder.ts#L232-L295)). Tool loops emit one `step.end` per model request and local tool result content events between requests ([docs/text/events.md:20-43](../../../docs/text/events.md#L20-L43)).
- `streamText` returns `{ stream, result }`. `result` resolves after the loop and includes all steps and summed usage. Cancelling the output stream rejects `result` and cancels the source. Aborting `signal` rejects with the abort reason ([packages/text/src/stream-text.ts:8-71](../../../packages/text/src/stream-text.ts#L8-L71), [docs/text/generating.md:49-89](../../../docs/text/generating.md#L49-L89)).
- Responses normalizes reasoning, refusals, tool calls, citations in text metadata, and unknown output items as `provider` Parts. It handles `response.done`, incomplete status, failed status, and missing terminal events ([packages/text-responses/src/utils/responses-event-stream.ts:116-212](../../../packages/text-responses/src/utils/responses-event-stream.ts#L116-L212), [packages/text-responses/test/response-done.test.ts:27-96](../../../packages/text-responses/test/response-done.test.ts#L27-L96)). `includeRawEvents: true` exposes every wire event as a `raw` TextEvent ([packages/text/src/utils/event-builder.ts:323-360](../../../packages/text/src/utils/event-builder.ts#L323-L360), [packages/text-responses/test/raw-events.test.ts:8-74](../../../packages/text-responses/test/raw-events.test.ts#L8-L74)). It has no normalized `search` or `citations` StreamEvent and no adapter callback equivalent to AIRI's `onNativeEvent`.

### AIRI

- AIRI still depends on the 0.5.1 API in its catalog and core agent: `@xsai-ext/responses`, `@xsai/shared-chat`, `@xsai/stream-text`, `@xsai/tool`, and related packages ([pnpm-workspace.yaml:258-274](https://github.com/moeru-ai/airi/blob/3b0672e3668bd1ade1210e579818f379e4f8a224/pnpm-workspace.yaml#L258-L274), [packages/core-agent/package.json:57-65](https://github.com/moeru-ai/airi/blob/3b0672e3668bd1ade1210e579818f379e4f8a224/packages/core-agent/package.json#L57-L65)). The old `streamText` takes one options object, exposes callback events, and returns separate `messages`, `steps`, `generatedTurn`-style data through AIRI's adapter code ([xsAI 0.5.1 streamText contract](https://github.com/moeru-ai/xsai/blob/c63fe0406b8b63cf54a83256c9fea7e52eb1a650/packages/stream-text/src/index.ts#L26-L59)).
- AIRI already owns a protocol-neutral boundary. `StreamEvent` covers text, reasoning, tool calls and results, errors, search, and citations ([packages/core-agent/src/types/llm.ts:17-28](https://github.com/moeru-ai/airi/blob/3b0672e3668bd1ade1210e579818f379e4f8a224/packages/core-agent/src/types/llm.ts#L17-L28)). `core-agent/runtime/xsai-events.ts` maps provider events to this UI/runtime vocabulary ([packages/core-agent/src/runtime/xsai-events.ts:1-45](https://github.com/moeru-ai/airi/blob/3b0672e3668bd1ade1210e579818f379e4f8a224/packages/core-agent/src/runtime/xsai-events.ts#L1-L45)). The migration can update this existing mapper and the existing `chat-completions.ts` and `responses.ts` adapters. It does not need a new universal wrapper.
- AIRI's domain model has richer input media. `InputSegment` includes audio, file data, file URL, provider file ID, and file name ([packages/core-agent/src/messages/types.ts:111-123](https://github.com/moeru-ai/airi/blob/3b0672e3668bd1ade1210e579818f379e4f8a224/packages/core-agent/src/messages/types.ts#L111-L123)). The current Responses adapter rejects audio and provider file references ([packages/core-agent/src/runtime/responses.ts:22-30](https://github.com/moeru-ai/airi/blob/3b0672e3668bd1ade1210e579818f379e4f8a224/packages/core-agent/src/runtime/responses.ts#L22-L30)). The current Chat adapter writes audio and provider file IDs to its old wire shape ([packages/core-agent/src/messages/chat-completions.ts:22-31](https://github.com/moeru-ai/airi/blob/3b0672e3668bd1ade1210e579818f379e4f8a224/packages/core-agent/src/messages/chat-completions.ts#L22-L31), `:76-84`).
- AIRI stores native provider state as a scoped `ProviderContinuation`. It keeps exact Chat messages or Responses items and scopes them to provider identity, endpoint, model, and conversation. Credentials and headers do not enter this scope ([packages/core-agent/src/messages/types.ts:148-157](https://github.com/moeru-ai/airi/blob/3b0672e3668bd1ade1210e579818f379e4f8a224/packages/core-agent/src/messages/types.ts#L148-L157), [packages/core-agent/src/runtime/request-context.ts:43-49](https://github.com/moeru-ai/airi/blob/3b0672e3668bd1ade1210e579818f379e4f8a224/packages/core-agent/src/runtime/request-context.ts#L43-L49)). This is different from xsAI `providerMetadata` and `provider` Parts. Those are message or Part data. They do not define replay scope.
- AIRI already keeps provider transcripts and generated turns when it builds history ([packages/core-agent/src/types/chat.ts:46-82](https://github.com/moeru-ai/airi/blob/3b0672e3668bd1ade1210e579818f379e4f8a224/packages/core-agent/src/types/chat.ts#L46-L82), [packages/core-agent/src/runtime/chat-orchestrator-runtime.ts:611-631](https://github.com/moeru-ai/airi/blob/3b0672e3668bd1ade1210e579818f379e4f8a224/packages/core-agent/src/runtime/chat-orchestrator-runtime.ts#L611-L631)). Existing Responses tests prove that AIRI replays unknown native items only in the matching scope, preserves them without a partial schema, and falls back to portable content after a scope change ([packages/core-agent/src/runtime/responses.test.ts:570-598](https://github.com/moeru-ai/airi/blob/3b0672e3668bd1ade1210e579818f379e4f8a224/packages/core-agent/src/runtime/responses.test.ts#L570-L598)).
- AIRI's Responses patch adds web search item types and `onNativeEvent`, forwards every native event, and throws on error and incomplete Responses events ([patches/@xsai-ext__responses@0.5.1.patch:5-50](https://github.com/moeru-ai/airi/blob/3b0672e3668bd1ade1210e579818f379e4f8a224/patches/@xsai-ext__responses@0.5.1.patch#L5-L50), `:52-96`). AIRI uses those events for search status and citations ([packages/core-agent/src/runtime/responses.ts:251-270](https://github.com/moeru-ai/airi/blob/3b0672e3668bd1ade1210e579818f379e4f8a224/packages/core-agent/src/runtime/responses.ts#L251-L270)).
- AIRI's tool contract uses the old `{ type: 'function', function: { name, parameters }, execute }` shape. The old execute context contains `abortSignal`, `messages`, and `toolCallId` ([xsAI 0.5.1 tool contract](https://github.com/moeru-ai/xsai/blob/c63fe0406b8b63cf54a83256c9fea7e52eb1a650/packages/shared-chat/src/types/tool.ts#L30-L45)). AIRI's serializable Stage tool store also persists the old `function` shape ([packages/stage-ui/src/stores/ai/chat-llm/tools.ts:7-61](https://github.com/moeru-ai/airi/blob/3b0672e3668bd1ade1210e579818f379e4f8a224/packages/stage-ui/src/stores/ai/chat-llm/tools.ts#L7-L61)). Some application tests pass `messages` and `toolCallId` to tools ([apps/stage-tamagotchi/src/renderer/stores/tools/builtin/weather.test.ts:185-199](https://github.com/moeru-ai/airi/blob/3b0672e3668bd1ade1210e579818f379e4f8a224/apps/stage-tamagotchi/src/renderer/stores/tools/builtin/weather.test.ts#L185-L199)). This proves an audit is needed. It does not prove every production tool uses those fields.
- AIRI preserves tool media in its existing Responses path. A test expects text, image, and file tool output to become `input_text`, `input_image`, and `input_file` while the AIRI tool event keeps the original output ([packages/core-agent/src/runtime/responses.test.ts:815-838](https://github.com/moeru-ai/airi/blob/3b0672e3668bd1ade1210e579818f379e4f8a224/packages/core-agent/src/runtime/responses.test.ts#L815-L838)). The same path rejects audio before another request (`:875-883`).
- AIRI completes a turn only after all tool steps settle. `llm-service.ts` waits for the old SDK's full `steps` promise, then awaits the generated turn, emits `finish`, persists the turn, and observes usage ([packages/core-agent/src/runtime/llm-service.ts:149-225](https://github.com/moeru-ai/airi/blob/3b0672e3668bd1ade1210e579818f379e4f8a224/packages/core-agent/src/runtime/llm-service.ts#L149-L225)). Its own generation object records one round per model step ([packages/core-agent/src/runtime/generation.ts:45-80](https://github.com/moeru-ai/airi/blob/3b0672e3668bd1ade1210e579818f379e4f8a224/packages/core-agent/src/runtime/generation.ts#L45-L80)). Do not redefine xsAI `step.end` as a turn-end event. AIRI must wait for v1 `streamText.result` while it consumes the event stream.
- AIRI uses `abortSignal`, keeps partial interrupted UI state, and cancels the local request from Stage ([packages/core-agent/src/types/llm.ts:63-78](https://github.com/moeru-ai/airi/blob/3b0672e3668bd1ade1210e579818f379e4f8a224/packages/core-agent/src/types/llm.ts#L63-L78), [packages/core-agent/src/runtime/llm-service.ts:125-165](https://github.com/moeru-ai/airi/blob/3b0672e3668bd1ade1210e579818f379e4f8a224/packages/core-agent/src/runtime/llm-service.ts#L125-L165), [packages/stage-ui/src/stores/chat.ts:1368-1372](https://github.com/moeru-ai/airi/blob/3b0672e3668bd1ade1210e579818f379e4f8a224/packages/stage-ui/src/stores/chat.ts#L1368-L1372)). v1 names the field `signal` and rejects the operation on abort.

## Confirmed gaps and severity

1. Hard gap for a direct shared media projection: AIRI can load audio and provider file IDs. xsAI v1 has no audio Part and no file ID or file name field. AIRI can preserve these inputs in an AIRI-owned native projection, but that keeps the behavior outside the shared v1 contract.
2. Hard gap for current tool output behavior: xsAI tool results allow text and image only. AIRI's current Responses tests preserve file output. AIRI can keep a provider-specific escape path, or xsAI can add file content to the v1 tool result contract.
3. Native event delivery is an integration choice, not a confirmed blocker. v1 already exposes every Responses wire event through one returned stream when `includeRawEvents` is enabled. AIRI can read that stream in its existing Responses adapter and map search and citation events. A typed callback can reduce adapter code, but it is optional.
4. Dynamic provider configuration is a design condition. v1 `prepareStep` can return a different `LanguageModel`, but a model function keeps its endpoint and transport settings. AIRI's current code mutates old request options inside `prepareStep` ([packages/core-agent/src/runtime/chat-completions.ts:38-79](https://github.com/moeru-ai/airi/blob/3b0672e3668bd1ade1210e579818f379e4f8a224/packages/core-agent/src/runtime/chat-completions.ts#L38-L79), [packages/core-agent/src/runtime/responses.ts:186-238](https://github.com/moeru-ai/airi/blob/3b0672e3668bd1ade1210e579818f379e4f8a224/packages/core-agent/src/runtime/responses.ts#L186-L238)). The existing AIRI `resolveStep` and `RequestSwitch` already create a new stream when the protocol or scope changes ([packages/core-agent/src/runtime/llm-service.ts:278-329](https://github.com/moeru-ai/airi/blob/3b0672e3668bd1ade1210e579818f379e4f8a224/packages/core-agent/src/runtime/llm-service.ts#L278-L329)). The v1 cutover must make the new model or transport selection explicit. AIRI must not mutate a v1 model function.
5. Tool execution context needs a production-use audit. v1 passes only `{ signal }`; old AIRI tools can receive `messages` and `toolCallId`. The scan found tests that pass those fields, but it did not confirm a production tool dependency. AIRI can remove the old context or provide it from its own closure. A v1 `callId` field is an optional compatibility convenience.
6. Incomplete and max-step behavior needs an explicit policy. v1 returns `incomplete` as a status, and its default loop limit is ten steps. AIRI's old Responses patch throws on incomplete, and AIRI rejects a completed generation that ends in an unresolved tool call ([packages/core-agent/src/runtime/generation.ts:67-80](https://github.com/moeru-ai/airi/blob/3b0672e3668bd1ade1210e579818f379e4f8a224/packages/core-agent/src/runtime/generation.ts#L67-L80)). AIRI must preserve that user-visible policy at its adapter boundary. xsAI must document that `step.end` remains per request and `streamText.result` represents loop completion.

## xsAI 1.0 recommendations

These are recommendations for the 1.0 decision. They are not design decisions.

### Existing v1 API to retain

1. Retain `LanguageModel`, the three adapter functions, `Message`, `TextEvent`, `streamText`, and `generateText`. The v1 model function and operation signatures already provide the clean public boundary. The old one-argument `streamText(options)` contract is already absent from the v1 API.
2. Retain the current message, provider Part, raw event, tool loop, cancellation, and terminal event semantics. One `step.end` belongs to one model request. The aggregate `result` belongs to the complete loop.

### Proposed public changes before 1.0

1. Add a first-class input media contract for audio and provider file references. Include the file name where the wire protocol needs it. Add file content to tool results. Define how each adapter rejects unsupported media.
2. Define per-step model and transport selection. `prepareStep` can already return a model. xsAI can document this as the supported way to change endpoint, credentials, headers, or protocol. If that contract is not enough, add a typed transport override before 1.0. AIRI must not mutate a model function's captured `HttpOptions`.

### Optional conveniences

1. Add a typed native event callback only if adapter authors need it. The existing `includeRawEvents` stream already carries the full Responses event sequence, so a callback is not required for the AIRI migration.
2. Add `callId` to tool execution options if the production-use audit finds a real need. Keep full conversation history outside the generic tool context. The existing `{ signal }` context remains sufficient for tools that only need cancellation.
3. Keep incomplete status and max-step behavior as documented. AIRI can apply its existing failure policy at its adapter boundary without changing the v1 terminal event model.

## AIRI preparation

The two groups have different dependencies. The first group can land while AIRI still uses 0.5.1. The second group requires the v1 packages.

### Safe preparation while AIRI uses 0.5.1

1. Inventory old imports, old tool definitions, media variants, option names, cancellation paths, and production tool execute context. Keep the audit separate from test-only calls that pass `messages` or `toolCallId`.
2. Add characterization fixtures and tests around the existing adapters. Cover scoped native continuation, unknown Responses items, search and citations, parallel tools, file and image tool output, protocol switching, transient retry, cancellation, and turn completion.
3. Keep AIRI's existing `core-agent/runtime/chat-completions.ts`, `responses.ts`, and `xsai-events.ts` boundary. Move SDK-specific types behind those existing files where a type-only refactor does not alter 0.5.1 behavior. Do not add a new runtime wrapper.
4. Keep `ProviderContinuation`, its scope, `generationTranscript`, and `providerTranscript` in AIRI. Use tests to prove that provider continuation remains separate from xsAI message metadata.
5. Add UI and configuration snapshots for Stage. These fixtures can verify that the later cutover preserves persisted history, interrupted replies, cancel, retry, and tool rerun behavior.

### Cutover work after xsAI v1 is available

1. Update the existing runtime adapters and `xsai-events.ts` to consume v1 models and TextEvents. Keep `core-agent/types/llm.ts` as the AIRI UI/runtime event boundary.
2. Map `abortSignal` to `signal` and `maxTokens` to `maxOutputTokens` inside the existing adapters. Keep the public Stage options and stored configuration unchanged.
3. Convert AIRI tools at the existing core boundary to `{ name, description, inputSchema, execute }`. Keep AIRI's stable application `id`, activation policy, and executor map. Remove old `function` and `parameters` shapes after all consumers move. Apply the production-use audit for `messages` and `toolCallId`.
4. Build a v1 model from each resolved provider step. Use `prepareStep` for input, tools, sampling, and other per-request fields. Use AIRI's existing `RequestSwitch` path when protocol, endpoint, model, or provider identity changes.
5. Read the v1 event stream in the existing adapter and await `streamText.result` before `onGeneratedTurn` and persistence. Preserve the current partial interrupted message, retry-before-first-event rule, and cancellation behavior. Apply AIRI's existing policy to an `incomplete` result.
6. Preserve exact v1 assistant messages and all step messages when AIRI builds the next request. Keep the existing fixtures as migration gates.
7. Migrate Stage first, then update the other monorepo consumers. Remove the 0.5.1 catalog entries and the Responses patch only after v1 tests replace their behavior. The initial inventory includes Stage, core-agent, provider-inference, component calling, Minecraft, Telegram, Satori, Discord, and game plugins.

## Acceptance evidence

- xsAI tests cover the v1 message and media shapes, Chat/Messages/Responses projections, file and image tool output, the selected tool context and cancellation, per-step model selection, native event observation, `response.done`, incomplete status, truncation, and output stream cancellation.
- AIRI core-agent tests pass for portable history, scoped native continuation, unknown Responses items, search and citations, parallel tools, media output, protocol switching, transient retry, and partial cancellation. The test suite proves that `onGeneratedTurn` runs only after the full loop result settles.
- Stage tests keep the existing UI and configuration behavior, including persisted `providerTranscript` and `generationTranscript`, interrupted replies, cancel, retry, and tool rerun behavior.
- A repository search finds no old `@xsai/*@0.5.1` text imports or old `function` tool definitions outside an intentional migration helper. The patched `@xsai-ext/responses@0.5.1` dependency and patch file are removed.

## Research limits

This research inspects source contracts. It does not establish runtime compatibility through tests or live provider calls.
